# Phase: design-explore

Absorbs: gstack design-consultation, design-shotgun, design-html, design-review · OMC designer · Superpowers brainstorming visual companion.

Full mode with a UI (plan `"ui": true`, Web or iOS); in Standard only when the user asks. `mis approve plan` refuses a Full UI plan until a design choice is recorded with `mis note design`.

0. `mis taste show` lists what this user approved and rejected before (fonts, palettes, layouts); let it steer the proposal and the variants, and say so.
1. **Design system proposal** (`DESIGN.md`, gstack design-consultation): product context, aesthetic, typography (up to 3 fonts with roles), color tokens (hex), spacing scale, layout, motion — with a one-line reason each, which choices are SAFE (category baseline) and at least two deliberate RISKS. Reuse an existing design system if the project has one. Avoid default-looking output (Inter/Roboto/Arial as the only type, purple gradients, uniform card grids).
   When the project has no design system yet, also write `design/preview.html`: each font in its role and the palette as swatches with hex values and text-contrast ratios, so the user judges the system, not only a screen.
2. **Variants** (gstack design-shotgun): 2-3 static mockups of the key screen that differ in typography, palette, and layout (if you can swap headlines between two and not notice, they are too similar). Web: self-contained HTML files with real content (no lorem ipsum), checked at 375 / 768 / 1440 px widths. iOS: SwiftUI views with `#Preview`. Put them under `design/` (they are deliverables the user reviews).
   Then `mis design-board design` writes `design/board.html`: every variant side by side in a frame with a `Choose` button (`data-choice`). Open that page through the companion. For each round of feedback, write new variant files and run `mis design-board` again.
3. Show them with the visual companion: `mis companion start design` serves `design/` on localhost (page index, live reload when you edit a file; elements with `data-choice="<id>"` are clickable). Give the user the **full** URL it prints (it carries the access key), say in one line what each variant is, and ask them to choose (or combine) in the terminal. Write each revision as a new file (`layout-v2.html`), never overwrite the one being judged. `mis companion status` lists the user's clicks — the terminal answer wins if they differ. `mis companion stop` when the choice is recorded. No browser available (remote/headless): list the file paths instead. Non-interactive: do not choose for the user; stop at the approval gate with the variants listed.
4. Taste: `mis taste approve <variant> --tags <font,palette,layout words>` for the chosen variant and `mis taste reject <variant> --tags ...` for the others.
   Record the choice **after the final `mis plan set`**: `mis note design - <<'MIS'` with the chosen variant, the reasons, and the final tokens. The note is bound to the current plan; any later plan change needs the note recorded again. Update `DESIGN.md` accordingly.
5. After implementation, the qa phase checks the built UI against `DESIGN.md` (hierarchy, spacing, color, states, responsiveness).
6. **Finalize** (gstack design-html): implementation turns the chosen mockup into production HTML/CSS with the project's own components and tokens, with real content, every state (loading, empty, error) and 375 / 768 / 1440 px widths; dispatch `make-it-ship:designer` for it.
7. **Outside a run** (the user only wants a design system, mockups or a diagram): the same steps without a run. Files go only to `design/` and `DESIGN.md`; no code changes.
