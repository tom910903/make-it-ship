# Phase: design-explore

Absorbs: gstack design-consultation, design-shotgun, design-html, design-review · OMC designer · Superpowers brainstorming visual companion.

Full mode with a UI (plan `"ui": true`, Web, iOS or Android); in Standard only when the user asks. `mis approve plan` refuses a Full UI plan until a design choice is recorded with `mis note design`.

0. `mis taste show` lists what this user approved and rejected before (fonts, palettes, layouts); let it steer the proposal and the variants, and say so.
   **References and current trends**: before proposing, look at what good products of this kind do now, on each platform the plan targets (web, desktop, iOS, Android).
   - Read the platform's current guidelines and what changed in them: Apple Human Interface Guidelines (iOS, iPadOS, macOS), Material Design (Android), Fluent (Windows). An app should feel native to its platform before it feels on-trend.
   - Search the web (WebSearch and WebFetch, or `mis browse goto` and `mis browse screenshot` on a public page) with generic terms for the category, the pattern and the platform, such as "analytics dashboard 2026", "iOS onboarding" or "3D product configurator"; no company or product details go into a search. Look at shipped products: live sites, public app store pages, design award winners.
   - Pick 3 to 6 references and write `design/references.md`: the date and the searches; for each reference its URL, the platform, a screenshot under `design/references/`, what to borrow (layout, type, color, motion, 3D use) and what to avoid; then the trends you saw, each with its source URL. Borrow principles, never a brand's assets or text. The proposal below says which reference each choice comes from.
   - Screenshots: `mis browse goto <url>`, then `mis browse prettyscreenshot --scroll-to "<a heading of the part that matters>" design/references/<name>.png`. Scrolling there loads its lazy images; a whole page can be tens of thousands of pixels tall. Add `--cleanup` only when a cookie or promo banner covers the part, and look at the result: removing banners can break a page's layout (it did on an App Store page). The guideline's own change log is text: read it with `mis browse text`.
1. **Design system proposal** (`DESIGN.md`, gstack design-consultation): product context, aesthetic, typography (up to 3 fonts with roles), color tokens (hex), spacing scale, layout, motion — with a one-line reason each, which choices are SAFE (category baseline) and at least two deliberate RISKS. Reuse an existing design system if the project has one. Avoid default-looking output (Inter/Roboto/Arial as the only type, purple gradients, uniform card grids).
   When the project has no design system yet, also write `design/preview.html`: each font in its role and the palette as swatches with hex values and text-contrast ratios, so the user judges the system, not only a screen.
   **3D**, only when it earns its place (a product to turn around, spatial data, a scene that explains what a flat image cannot; never decoration that slows the screen): add a "3D and motion" section to `DESIGN.md`.
   - Library: the project's own first; otherwise by platform, and a new dependency needs the user's approval. Web, Electron and Tauri: three.js, or React Three Fiber in a React app. iOS, iPadOS, macOS and visionOS: RealityKit (SceneKit only where the app already uses it). Android: Filament or SceneView, or the app's own OpenGL ES or Vulkan view. React Native: React Three Fiber's native renderer. Flutter: the platform's 3D view embedded, or a package the user approves. Windows: DirectX in a SwapChainPanel (WinUI). Qt: Qt Quick 3D.
   - Budget: a frame rate (at least 50 fps on the target devices, 60 on desktop), the size of the 3D code and assets (glTF/GLB on the web and Android, USDZ on Apple platforms, compressed textures); the scene loads after the first screen is shown.
   - Reduced motion: hold a still frame (no auto-rotation, no parallax) when the platform asks for it: `prefers-reduced-motion` on the web and in Electron and Tauri; `accessibilityReduceMotion` (SwiftUI) or `UIAccessibility.isReduceMotionEnabled` on iOS; `NSWorkspace.shared.accessibilityDisplayShouldReduceMotion` on macOS; `ValueAnimator.areAnimatorsEnabled()` on Android; `UISettings.AnimationsEnabled` on Windows; `MediaQuery.disableAnimations` in Flutter; `AccessibilityInfo.isReduceMotionEnabled()` in React Native.
   - Fallback: a static image or 2D view with the same information when 3D is unavailable (no WebGL, an old GPU, a low-power mode) or fails; keyboard, switch and screen-reader access to whatever the 3D view controls.
   - The variants show the 3D idea as a still next to the 2D layout.
2. **Variants** (gstack design-shotgun): 2-3 static mockups of the key screen that differ in typography, palette, and layout (if you can swap headlines between two and not notice, they are too similar). Web: self-contained HTML files with real content (no lorem ipsum), checked at 375 / 768 / 1440 px widths. iOS: SwiftUI views with `#Preview`. Put them under `design/` (they are deliverables the user reviews).
   Then `mis design-board design` writes `design/board.html`: every variant side by side in a frame with a `Choose` button (`data-choice`). Open that page through the companion. For each round of feedback, write new variant files and run `mis design-board` again.
3. Show them with the visual companion: `mis companion start design` serves `design/` on localhost (page index, live reload when you edit a file; elements with `data-choice="<id>"` are clickable). Give the user the **full** URL it prints (it carries the access key), say in one line what each variant is, and ask them to choose (or combine) in the terminal. Write each revision as a new file (`layout-v2.html`), never overwrite the one being judged. `mis companion status` lists the user's clicks — the terminal answer wins if they differ. `mis companion stop` when the choice is recorded. No browser available (remote/headless): list the file paths instead. Non-interactive: do not choose for the user; stop at the approval gate with the variants listed.
4. Taste: `mis taste approve <variant> --tags <font,palette,layout words>` for the chosen variant and `mis taste reject <variant> --tags ...` for the others.
   Record the choice **after the final `mis plan set`**: `mis note design - <<'MIS'` with the chosen variant, the reasons, and the final tokens. The note is bound to the current plan; any later plan change needs the note recorded again. Update `DESIGN.md` accordingly.
5. After implementation, the qa phase checks the built UI against `DESIGN.md` (hierarchy, spacing, color, states, responsiveness).
6. **Finalize** (gstack design-html): implementation turns the chosen mockup into production HTML/CSS with the project's own components and tokens, with real content, every state (loading, empty, error) and 375 / 768 / 1440 px widths; dispatch `make-it-ship:designer` for it.
7. **Outside a run** (the user only wants a design system, mockups or a diagram): the same steps without a run. Files go only to `design/` and `DESIGN.md`; no code changes.
