# Make It Ship — 제품 기획서 (PRD)

> **From Idea to Verified Software**  
> 아이디어를 전달하면, AI 개발팀이 계획하고 만들고 검증한 뒤 결과를 설명한다.

| 항목 | 내용 |
|---|---|
| 제품명 | **Make It Ship** |
| 문서 유형 | **제품·서비스 기획서 (Product Requirements Document)** |
| 문서 버전 | 1.0 — 개발 전 기획 기준안 |
| 작성일 | 2026-10-19 |
| 초기 제공 형태 | Claude Code용 개발 워크플로 플러그인 |
| 초기 지원 환경 | macOS / Apple Silicon, Git 기반 프로젝트 |
| 확장 목표 | Linux 및 다른 AI 코딩 에이전트로 확장 |
| 핵심 참고 프로젝트 | OMC · Superpowers · gstack · Ponytail |
| 문서 상태 | 기획 초안. 사용자 검토 후 요구사항과 우선순위를 확정한다. |

> **문서의 목적**: 무엇을, 왜, 누구를 위해 만들지 정의한다. 구현 언어·클래스·DB 스키마·훅·API 등 상세 기술 설계는 별도 개발 설계서에서 다룬다. 이 문서에 나오는 명령·화면·지표는 **Make It Ship의 제안 사양**이지 현재 사용 가능한 기능이 아니다.

## 1. 한눈에 보는 제품

### 1.1 한 문장 정의

**Make It Ship은 아이디어, 요구사항 문서 또는 기존 코드의 변경 요청을 받아, AI 에이전트들이 계획·구현·테스트·리뷰·검증·결과 보고까지 수행하도록 안내하고 관리하는 AI 소프트웨어 개발 워크플로 제품이다.**

### 1.2 해결하려는 핵심 문제

AI 코딩 도구만으로도 코드를 빠르게 작성할 수 있지만, 사용자가 실제 개발 책임자처럼 다음 문제를 계속 챙겨야 한다.

1. 요구사항을 제대로 이해했는지 반복 확인해야 한다.
2. 여러 에이전트·스킬·플러그인이 서로 중복된 계획과 리뷰를 수행한다.
3. 테스트하지 않은 코드를 완료했다고 보고하거나, 테스트 결과와 코드 버전이 일치하지 않는다.
4. 간단한 변경에 과도한 추상화·의존성·에이전트가 동원된다.
5. 장시간 작업이 중단되면 진행 상태와 미해결 문제가 사라진다.
6. 기능 구현은 끝났지만 실제 사용자 시나리오·배포 준비·결과 설명이 빠진다.

### 1.3 제공 가치

- **한 번의 의뢰**: 사용자는 구현 수단보다 원하는 결과와 제약을 전달한다.
- **일관된 작업 흐름**: 계획→개발→검증의 책임과 순서를 하나로 정리한다.
- **확인 가능한 완성도**: “완료” 대신 무엇을 실제로 빌드·테스트·검토했는지 보여준다.
- **적정한 복잡성**: 작은 작업은 가볍게, 큰 작업은 분업하여 진행한다.
- **통제 가능한 자율성**: 위험한 작업은 승인받고, 중간에 중단·재개할 수 있다.

### 1.4 제품 약속

> **Build it. Prove it. Show it.**  
> 만들고(Build), 검증하고(Prove), 결과를 설명한다(Show).

**범위 정의**: `Ship`은 기본적으로 **검증된 결과물과 배포 가능한 변경 집합을 준비한다**는 의미다. 사용자의 명시적 승인 없이 실제 프로덕션 배포·원격 푸시·파괴적 변경을 수행한다는 뜻이 아니다.

## 2. 제품 배경과 기회

### 2.1 왜 기존 프로젝트 네 개를 참고하는가?

| 참고 프로젝트 | 강점으로 채택할 제품 경험 | Make It Ship이 해결할 과제 |
|---|---|---|
| **OMC (Oh My Claude Code)** | 전문 에이전트 협업, 작업 분담, 병렬 실행, 검증 반복 | 한 제품 안에서 작업 실행의 책임을 일원화 |
| **Superpowers** | 계획 우선, TDD, 근본 원인 디버깅, 단계별 리뷰 | 사용자가 매번 개발 절차를 지시하지 않아도 적용 |
| **gstack** | 제품 관점 재검토, 사용자 경험 검증, QA, 출시 전 점검 | 코드 단위 성공을 실제 제품 성공으로 연결 |
| **Ponytail** | 재사용 우선, YAGNI, 간결한 변경, 불필요한 의존성 억제 | 품질을 해치지 않는 범위에서 과설계 억제 |

**핵심 전략**: 네 플러그인을 동시에 켜서 기능 수를 늘리는 것이 아니라, **겹치는 기능은 하나의 사용자 경험과 책임 체계로 정리**한다. 외부 스킬·프로젝트의 코드를 반드시 사용한다는 뜻은 아니며, 초기에는 개발 철학과 검증된 작업 방식부터 반영한다.

### 2.2 기존 선택지와 차별점

| 기존 선택지 | 일반적 강점 | Make It Ship의 목표 차별점 |
|---|---|---|
| Claude Code / Codex 기본 기능 | 유연한 코딩, 높은 범용성 | 기획부터 완료 판정까지 고정된 책임·품질 기준 |
| OMC 단독 | 작업 병렬화와 오케스트레이션 | 단순성·제품 QA·결과 증거까지 일관되게 연결 |
| Superpowers 단독 | 개발 절차의 엄격함 | 작업 규모별 경량화와 팀 실행 관리 |
| gstack 단독 | 제품 및 출시 관점 검토 | 긴 작업의 단일 진행 상태 및 개발 과정 통합 |
| Ponytail 단독 | 간단하고 효율적인 구현 | 제품 목표·테스트·배포 준비까지 관리 |
| 네 플러그인 개별 설치 | 모든 개별 기능을 직접 사용 가능 | 중복 동작을 줄이고 **한 번에 일관되게 작동** |

이 표는 **제품 포지셔닝**이며, 경쟁 프로젝트가 특정 기능을 전혀 제공하지 않는다는 의미는 아니다.

## 3. 목표 사용자

### 3.1 핵심 사용자: 소수 인원의 시니어 개발자·PL

- **상황**: Git 저장소에 요구사항 문서를 준비하고 Claude Code로 개발을 위임한다.
- **불편**: 에이전트를 직접 호출하고 설계·리뷰·테스트 상태를 계속 따라가야 한다.
- **원하는 결과**: 자신은 요구사항과 최종 중요한 결정을 담당하고, 나머지 개발 절차는 자동화한다.
- **대표 예시**: macOS에서 Python/Swift/Flutter 앱을 개발하거나 Linux·Yocto 프로젝트를 유지보수하는 엔지니어.

### 3.2 확장 사용자

| 페르소나 | 주요 니즈 | 초기 중요도 |
|---|---|---|
| 1인 개발자·사이드 프로젝트 창업자 | 아이디어에서 실행 가능한 MVP까지 빠르게 구현 | 높음 |
| 개발팀 리더·테크 리드 | 개발 품질과 리뷰 절차를 표준화 | 높음 |
| 중소 개발팀 | 반복적인 품질 점검과 작업 위임 | 중간 |
| 코딩 초보자 | 복잡한 구현 과정을 안내받고 결과 확인 | 장기 |

**초기 제품은 비개발자를 위한 완전 무인 앱 제작 서비스가 아니다.** Git, 프로젝트 실행·테스트 환경을 다룰 수 있는 개발자를 주요 고객으로 가정한다.

### 3.3 핵심 사용자 요구(JTBD)

- 내가 *요구사항 문서를 전달하면*, AI가 *작업 계획을 수립하고 구현을 시작*했으면 한다.
- 내가 *복잡한 기능을 요청하면*, AI가 *독립 작업을 분리·병렬화하고 충돌을 관리*했으면 한다.
- 내가 *완료 결과를 받으면*, *빌드·테스트·리뷰의 근거*를 함께 확인하고 싶다.
- 내가 *간단한 버그를 요청하면*, *불필요한 설계 회의 없이 안전하게 최소 수정*했으면 한다.
- 작업이 *중단되거나 비용 한도에 도달하면*, *유실 없이 재개할 지점과 미해결 사항*을 알고 싶다.
- 내가 *배포나 원격 저장소 변경을 요청하더라도*, *위험도가 큰 실행은 사전에 승인*하고 싶다.

## 4. 제품 비전·목표·비목표

### 4.1 비전

**개발자가 요구사항과 중요한 의사결정에 집중할 수 있도록, AI 개발 조직의 작업 과정을 표준화하고 검증 가능한 결과물을 제공한다.**

### 4.2 1차 목표

1. 요구사항을 받아 실행 가능한 계획과 작업 단위로 변환한다.
2. 작업 성격에 적합한 개발 워크플로를 자동 선택한다.
3. 설계·개발·테스트·리뷰·결과 보고를 하나의 진행 상태로 연결한다.
4. 검증 증거 없는 ‘완료’ 선언을 막는다.
5. 소스 변경·외부 행위·비용을 사용자가 통제할 수 있게 한다.
6. 기존 코드 및 의존성을 우선 활용하여 과설계를 억제한다.

### 4.3 초기 비목표 (의도적으로 제외)

- 사람의 개입이 전혀 없는 프로덕션 자동 배포
- 새 AI 기초 모델의 학습·파인튜닝
- 모든 개발 언어·프레임워크에서 동일한 수준의 자동 테스트 보장
- 모든 종류의 디자인 작업에 대한 완전 자동 UX 적합성 평가
- 4개 외부 프로젝트의 전체 코드를 통째로 합치는 것
- 자체 IDE/웹 대시보드·클라우드 서비스·계정 시스템을 MVP에서 구축하는 것
- 높은 테스트 커버리지 수치만으로 제품 완성도를 보증하는 것

## 5. 제품 사용 경험

### 5.1 핵심 이용 흐름

```text
아이디어 / 요구사항.md / 기존 저장소
              ↓
     요청 이해 및 범위 판단
              ↓
       개발 경로 자동 선택
        Quick / Standard / Full
              ↓
        구현 계획 및 승인*
              ↓
        구현 + 개발 품질 원칙
              ↓
       빌드 / 테스트 / 리뷰
              ↓
      실제 사용 시나리오 검증
              ↓
        결과·근거·한계 보고
              ↓
     사용자의 최종 채택·출시 결정
```

\* 큰 변경·위험한 변경은 계획 또는 실행 승인 필요. 안전한 소규모 변경은 사용자 설정에 따라 간소화할 수 있다.

### 5.2 개발 경로 3종

| 구분 | Quick | Standard | Full |
|---|---|---|---|
| 사용 상황 | 작은 버그, 단순 코드 수정 | 일반 기능 추가·중간 규모 변경 | 새 프로젝트, 대규모 리팩터링, 복합 기능 |
| 계획 | 변경 요약 중심 | 작업 계획 | 요구사항 재검토 + 범위·의존성 계획 |
| 실행 | 단일 에이전트 우선 | 필요 시 분업 | 독립 가능한 작업은 병렬 협업 |
| 검증 | 관련 테스트 및 핵심 확인 | 테스트 + 독립 리뷰 | 테스트 + 다각도 리뷰 + 적합한 QA |
| 사용자 개입 | 최소화 | 주요 결정 승인 | 계획·위험·출시 단계 승인 |

**모드 선택은 작업 규모만이 아니라 위험도도 반영**해야 한다. 보안·데이터 마이그레이션 등 위험한 변경은 코드가 짧아도 엄격하게 검증한다.

### 5.3 사용자 시나리오 A — 요구사항 문서로 앱 만들기

**입력**: “이 `requirements.md`대로 macOS 앱을 개발해줘. 완료되면 실행 방법과 테스트 결과를 알려줘.”

1. 문서와 현재 저장소를 읽는다.
2. 목표·제약·누락된 핵심 조건만 정리한다.
3. 기능별 작업과 완료 조건을 제시한다.
4. 승인받은 계획에 따라 개발을 실행한다.
5. 자동화된 테스트와 실행 가능한 범위의 실제 동작 검증을 한다.
6. 실행 방법, 결과물, 통과·실패 항목, 남은 문제를 보고한다.

**성공 경험**: 사용자가 세부 스킬을 직접 호출하지 않고도, 무엇이 만들어졌고 어느 수준까지 확인되었는지 이해한다.

### 5.4 사용자 시나리오 B — 기존 저장소 버그 수정

**입력**: “이 이슈를 고쳐줘. 다른 API 동작은 바뀌면 안 돼.”

1. 변경 범위를 좁히고 재현·원인을 조사한다.
2. 재현 가능한 테스트가 있다면 우선 추가하거나 기존 테스트를 보강한다.
3. 필요한 최소 코드를 수정한다.
4. 회귀 테스트와 영향 범위 리뷰를 실행한다.
5. 수정 파일, 원인, 증거, 남은 위험을 요약한다.

**성공 경험**: 빠르고 작은 수정이면서 기존 기능의 회귀 위험을 확인할 수 있다.

### 5.5 사용자 시나리오 C — 작업 중단과 재개

**상황**: AI 작업 중 세션 종료, 빌드 실패, API 호출 한도 또는 비용 한도 도달.

1. 완료된 단계와 미완료 작업을 구분해 저장한다.
2. 현재 코드 상태와 검증 결과의 연결 여부를 기록한다.
3. 재개 시 변경된 파일과 이전 작업 기록을 점검한다.
4. 실패 원인이 남아 있으면 ‘차단됨’으로 표시하고 안전한 조치를 안내한다.

**성공 경험**: 사용자가 처음부터 다시 설명하지 않고도 안전하게 재개할 수 있다.

### 5.6 대화/명령 경험 예시

다음은 **목표 UX 예시**이며 확정된 CLI 명령이 아니다.

```text
사용자: Make It Ship, 이 requirements.md로 개발해줘.

Make It Ship:
- 작업 유형: Full
- 확인한 목표: 8개 기능 / 3개 주요 제약
- 먼저 결정할 사항: 2개
- 제안 계획: 12개 작업, 3개 독립 작업 그룹
- 필수 검증: 단위 테스트, 통합 빌드, 핵심 사용자 시나리오
- 승인 후 구현을 진행할 수 있습니다.

[개발 및 검증 후]

Make It Ship:
- 구현: 12개 작업 중 11개 완료 / 1개 차단
- 빌드: 통과
- 테스트: 96개 통과 / 2개 실패
- 리뷰: 중대 이슈 없음, 보통 이슈 1개
- 출시 준비 상태: PARTIAL — 미완료 1개·실패 2개 확인 필요
- 변경 요약 및 재현 명령: 첨부
```

**핵심 UX 원칙**: 막연한 “성공했습니다” 대신 **증거와 미해결 사항을 함께 보여준다**.

## 7. 일관된 개발 품질 원칙

### 7.1 품질 우선순위

**정확성·보안·데이터 안전성 → 요구사항 충족 → 검증 가능성 → 유지보수성 → 단순성 → 비용 효율**

간단하게 만들기 위해 테스트나 필수 오류 처리를 삭제하지 않는다. 테스트를 늘리는 것이 실사용 품질을 보장하지도 않으므로, 변경 위험에 맞는 검증을 선택한다.

### 7.2 네 프로젝트의 역할 분리

| 사용자에게 필요한 과정 | 대표적으로 참고할 관점 | 통합 제품의 규칙 |
|---|---|---|
| 무엇을 왜 만들지 결정 | gstack | 목적·제약·가치가 모호하면 질문하거나 가정 표시 |
| 계획을 작업으로 변환 | Superpowers | 검증 가능한 작업 단위와 수용 기준 작성 |
| 여러 작업을 나눠 실행 | OMC | 독립 작업만 병렬화, 전체 상태는 하나로 관리 |
| 테스트·디버깅 | Superpowers | 재현과 원인 분석 우선, 적합한 테스트 수행 |
| 과설계 방지 | Ponytail | 재사용과 최소 변경을 우선, 필수 보장은 보존 |
| 제품·사용자 흐름 검증 | gstack | 개발 유형에 맞는 QA 선택 |
| 결과 통합·보고 | Make It Ship 자체 | 미검증·차단·실패를 숨기지 않음 |

### 7.3 품질 검증 결과의 네 가지 상태

- **VERIFIED**: 정의한 수용 조건이 충족되고 해당 코드 상태에서 필요한 검증 증거가 존재함.
- **PARTIAL**: 상당 부분 구현했지만 미완료·미검증 또는 경미하지 않은 남은 문제가 존재함.
- **BLOCKED**: 권한, 환경, 의존성, 입력 정보 등으로 다음 단계 진행 불가.
- **FAILED**: 검증을 수행했고 수용 조건 또는 필수 테스트가 실패함.

**화면·보고 문구 규칙**: `PARTIAL`, `BLOCKED`, `FAILED`는 어떠한 경우에도 “배포 준비 완료”로 표시하지 않는다. 테스트 불가와 테스트 실패도 구분한다.

## 8. 자동화와 사용자 통제

### 8.1 자율 실행의 기본값

| 행위 | 기본 정책 | 이유 |
|---|---|---|
| 요구사항 읽기·코드 조사 | 허용 | 작업 이해에 필수 |
| 로컬 코드 작성·수정 | 합의한 프로젝트 범위에서 허용 | 자동 개발 가치 |
| 승인된 검증 명령 실행 | 허용(위험 명령 제외) | 실제 검증에 필요 |
| 추가 패키지 설치·외부 네트워크 접근 | 목적·범위·정책에 따라 안내 또는 승인 | 공급망·비용·보안 위험 |
| 원격 Push·PR 생성 | 명시적 사용자 요청 또는 승인 후 | 외부 시스템 변경 |
| 프로덕션 배포·데이터 삭제 | 반드시 별도 승인 | 되돌리기 어려운 위험 |
| API 키·비밀정보 외부 전송 | 기본 차단 | 보안 및 개인정보 보호 |
| 개발 규칙·권한 정책 변경 | 승인 후 적용 | 무단 행동 변경 방지 |

### 8.2 사용자에게 질문해야 하는 경우

- 제품 목표가 서로 모순되거나, 중요한 설계 대안 간 선택이 필요한 경우
- 예상되는 데이터 손실·보안·호환성 위험이 높은 경우
- 외부 서비스 변경 또는 승인되지 않은 비용 지출이 필요한 경우
- 작업 범위가 원래 요청에서 실질적으로 확대되는 경우

**반대로 이미 요구사항에 답이 있거나 안전한 기본값으로 해결 가능한 질문은 반복하지 않는다.**

### 8.3 중단·실패 경험

- 진행 불가 사유를 한 문장으로 요약한다.
- 마지막 성공 지점과 현재 소스 상태를 알려준다.
- 자동 복구할 수 있는 문제와 사용자 조치가 필요한 문제를 분리한다.
- 동일한 실패를 무한 반복하지 않고 제한된 재시도 후 중지한다.
- 비용 상한 초과 시 사용자 승인 없이는 추가 유료 실행을 계속하지 않는다.

## 10. 출시 및 제공 범위

### 10.1 초기 타깃 플랫폼

- **1차**: Claude Code + macOS + 로컬 Git 프로젝트
- **2차**: Linux 지원 확대, 다양한 개발 유형 검증
- **3차**: Codex 등 다른 실행 환경 및 상위 에이전트 연계

특정 외부 플러그인 4종의 설치를 사용자에게 강제하지 않는 방향을 우선한다.

### 10.2 초기 지원 시나리오

- **필수 데모 A**: TypeScript/Python 예제 저장소의 명확한 기능 추가
- **필수 데모 B**: 기존 기능의 버그 재현·수정·회귀 테스트
- **필수 데모 C**: Markdown 요구사항으로 작은 애플리케이션 완성
- **필수 데모 D**: 검증 실패·세션 중단 후 상태 확인 및 재개
- **추가 검증**: Swift/Flutter, Yocto·Linux BSP처럼 테스트 환경이 제한되는 프로젝트

BSP 프로젝트에서는 ‘실제 타깃 검증’을 수행하지 못했다면 **미검증으로 표시**해야 한다. 빌드 통과를 실제 하드웨어 동작 확인과 혼동하지 않는다.

### 10.3 배포 및 운영 정책 초안

- MVP는 개인·소규모 개발자 중심의 로컬 설치형 제품으로 제공한다.
- 서버·유료 구독·데이터 수집 서비스는 초기 구축 범위에서 제외한다.
- 오픈소스 공개 여부와 배포 라이선스는 별도 결정한다.
- 외부 프로젝트의 코드를 복제하는 경우 해당 저작권·라이선스 고지를 유지하고 버전을 관리한다.

## 11. MVP 정의: 어디까지 만들면 첫 번째 제품인가?

**MVP 성공 정의**: 개발자가 작은 Git 프로젝트에 대해 **요구사항 전달 → 계획 확인 → 코드 변경 → 실제 테스트·리뷰 → 근거 있는 결과 보고**까지 하나의 경험으로 완료할 수 있어야 한다.

### 11.1 MVP 필수 수용 기준

1. 사용자가 자연어 또는 `.md` 파일을 제공하면 목표·제약·완료 조건을 정리한다.
2. 작업을 Quick/Standard/Full 중 하나로 분류하고 변경 가능하게 한다.
3. 실행할 계획과 작업 목록을 한 곳에서 확인할 수 있다.
4. 사용자 승인 범위를 벗어나지 않고 실제 코드를 변경한다.
5. 적합한 테스트 또는 빌드를 **실제로 실행**하고, 불가능하면 그 사실을 표시한다.
6. 요구사항 적합성과 코드 품질을 점검한다.
7. 불필요한 의존성·구현을 추가하지 않도록 검토한다.
8. 코드가 달라지면 기존 검증의 유효성을 재판정한다.
9. 사용자에게 완료/부분완료/차단/실패 중 하나로 결과를 보고한다.
10. 작업 중단 후 마지막 기록된 지점과 미해결 문제를 재확인할 수 있다.
11. 원격 변경 또는 위험 작업은 명시적 승인 없이 실행되지 않는다.
12. 네 외부 플러그인을 별도로 설치하지 않아도 기본 시나리오를 수행할 수 있다.

### 11.2 MVP에서 일부러 하지 않을 것

- 복잡한 모델 자동 라우팅과 비용 최적화 알고리즘
- 수십 명 규모의 동시 에이전트 운영
- 범용 자동 프로덕션 배포
- 자체 브라우저 UI/대시보드
- 자동 프로세스 자가 수정
- 모든 프레임워크·언어의 완전한 QA 자동화

## 12. 단계별 제품 로드맵

| 단계 | 제품 목표 | 사용자에게 보이는 성과 | 종료 조건 |
|---|---|---|---|
| **M0 — 기획 검증** | 핵심 사용자·시나리오·우선순위 확정 | 문제·기대 결과·MVP 범위가 명확함 | 기획서 승인, 벤치마크 작업 정의 |
| **M1 — 핵심 경험** | 입력→계획→개발→검증→보고 | 단일 작업을 처음부터 끝까지 진행 | 기본 데모 A/B 통과 |
| **M2 — 신뢰성** | 리뷰·완료 판정·중단·재개 | 실패와 미검증을 구분하고 복구 | 데모 D 및 안전 정책 점검 |
| **M3 — 선택형 협업** | 독립 작업에 제한적 멀티 에이전트 활용 | 복잡한 작업의 분업 경험 | 충돌 관리 및 Full 경로 검증 |
| **M4 — 제품화** | 실제 QA·문서 정리·사용 경험 개선 | 새 사용자가 설치 후 작은 프로젝트 수행 | 데모 C, 사용법·제약 문서 준비 |
| **M5 — 확장** | 비용 관리·품질 정책·다중 실행 환경 | 더 다양한 프로젝트와 에이전트 지원 | 별도 확장 수용 기준 수립 |

**원칙**: 각 단계에서 동작하는 결과물을 확인한 뒤 다음 단계로 진입한다. 일정은 실제 개발 환경·난이도를 검증한 뒤 결정하며, 이 표는 개발 기간을 보장하지 않는다.

## 13. 성공 지표와 평가 방법

### 13.1 제품 성공 지표

| 지표 | 측정 방법 | 초기 파일럿 목표(제안) |
|---|---|---|
| 작업 완수율 | 합의된 수용 기준 충족 작업 / 전체 평가 작업 | 평가 집합의 **80% 이상** |
| 거짓 완료 선언 | 필수 검증 미통과·미실시인데 VERIFIED로 표시한 횟수 | **0건** |
| 사용자 개입 횟수 | 동일 과제 수행 중 필수 질문·수동 개입 횟수 | 비교 기준 대비 **감소** |
| 회귀 결함 | 이전 동작을 깨뜨린 자동화 결과 | 비교 기준 대비 **감소** |
| 중단 복구 성공률 | 정상적으로 상태 확인 및 재개가 가능한 사례 | 파일럿 **90% 이상** |
| 실행 비용 | 과제당 토큰/API 사용 비용 | 단독 Claude Code/OMC와 **비교 측정** |
| 만족도 | 결과 이해·신뢰성·개입 부담에 대한 사용자 평가 | 초기 사용자 인터뷰로 측정 |

이 숫자는 **개발 목표를 논의하기 위한 가설적 기준**이다. 현재 제품의 측정 결과나 성능을 뜻하지 않는다.

### 13.2 비교 평가 원칙

동일한 과제 집합으로 다음을 비교한다.

- Claude Code 기본 기능
- OMC 단독
- Make It Ship

가능하다면 Superpowers 단독 실행도 비교군에 포함한다. 동일한 모델·프로젝트 초기 상태·제약·평가 절차를 사용해야 하며, 토큰·시간 감소만을 성공으로 평가하지 않는다.

### 13.3 파일럿 과제 제안

1. 작은 Python CLI 기능 추가
2. 기존 TypeScript 유틸리티 버그 수정
3. 로그인 또는 권한 검증이 포함된 변경
4. UI 중심의 작은 화면 추가
5. 의존성이 있는 2~3개 모듈 동시 변경
6. 테스트 환경이 부족한 프로젝트의 정직한 검증 보고
7. 일부러 실패하는 테스트가 있는 저장소 처리
8. 중도 세션 종료 후 재개

## 15. 운영 원칙 및 장기 확장

### 15.1 제품 철학

- **Autonomy with Accountability**: 자율 실행하되 결과 책임과 검증 근거를 남긴다.
- **One Workflow, Many Specialists**: 전문 에이전트는 여럿이어도 사용자가 보는 개발 흐름은 하나다.
- **Risk-Aware Execution**: 변경 규모가 아닌 실제 위험도에 따라 승인·검증을 강화한다.
- **Simplicity without Sacrifice**: 보안을 희생하지 않는 단순화만 허용한다.
- **Human Owns the Ship Button**: 외부 공개·배포의 최종 책임은 사용자에게 있다.

### 15.2 장기 비전

향후 Jarvis 같은 상위 에이전트가 Make It Ship에 개발 업무를 위임할 수 있도록 확장한다. 단, 초기 제품에서는 Claude Code 사용자가 직접 의뢰하는 경험을 먼저 완성한다.

```text
사용자 / 상위 AI 에이전트
          ↓
     Make It Ship
          ↓
    계획 · 개발 · 검증
          ↓
  변경 결과 + 검증 증거
          ↓
       사용자 결정
```

### 15.3 제품 사용 정책

원격 코드·비밀정보·사용 데이터의 소유권은 사용자에게 있으며, 프로젝트 데이터는 기본적으로 로컬에서 관리한다. AI 모델 제공자에 대한 코드 전달 등 기존 코딩 에이전트의 데이터 처리까지 이 제품이 차단하거나 보증하는 것은 아니므로 설치·실행 안내에서 해당 한계를 명시한다.

## 17. 최종 제품 정의 및 출시 판단

### 17.1 이 제품이 성공한 모습

사용자가 `requirements.md` 하나를 건네고 개발을 맡기면 다음 결과를 받는다.

> “요청하신 기능 중 무엇을 구현했고, 어떤 검증이 통과했으며, 어디까지는 확인하지 못했고, 다음에 사용자가 무엇을 결정해야 하는지”가 명확한 개발 결과.

AI가 대단히 많은 코드를 작성했다거나 에이전트를 많이 동원했다는 사실은 성공의 기준이 아니다.

### 17.2 MVP 출시 판단 질문

- 실제 사용자가 세부 스킬을 배우지 않고도 작업을 끝까지 진행할 수 있는가?
- 작업의 품질 검증이 소스 상태와 연결되는가?
- 검증 실패·미실시를 완료로 잘못 보고하지 않는가?
- 짧은 수정이 불필요하게 복잡한 프로세스로 바뀌지 않는가?
- 중단된 작업을 안전하게 다시 시작할 수 있는가?
- 사용자가 예상치 못한 위험한 외부 변경을 당하지 않는가?

위 질문에 검증 가능한 답을 제시할 수 있을 때 첫 제품이 성립한다.
